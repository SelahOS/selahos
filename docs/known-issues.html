Beta 2.0.1

Known issues & workarounds

Two real, currently-unsolved hardware issues on some Apple Macs, explained plainly, with workarounds you can use today while we work on real fixes for Beta 2.0.2.

Our policy: we don't publish a fix here until it's real and tested. Both issues below are open. What you'll find instead is an honest explanation, a practical way to keep working around it, and (for the technically inclined) the exact diagnostic scripts we're using ourselves, in case you want to help investigate.

Wi-Fi association hangs on some Apple Broadcom cards Active

On some Macs (confirmed so far: MacBook 10,1 and iMac16,2), connecting to Wi-Fi for the first time can hang indefinitely at "connecting" instead of either succeeding or failing. This isn't a driver quality problem — SelahOS uses the same mainline Linux Wi-Fi driver every other distro uses for this hardware. The real cause is that Apple's per-board radio calibration data isn't published anywhere we can verify, so the chip falls back to a generic configuration that doesn't fully work with every network.

Workaround

Use a wired Ethernet connection, or a USB Wi-Fi adapter, until this is resolved. Both work normally — this issue is specific to the built-in Apple Wi-Fi hardware, not to networking on SelahOS in general.

Technical detail + a script to try (for advanced users)

Affected chips log messages like this in journalctl -k: 

brcmfmac: brcmf_c_process_clm_blob: no clm_blob available (err=-2), device may have limited channels available

This script sets an explicit Wi-Fi regulatory domain and captures a detailed log of your next connection attempt. It's safe and fully reversible — it doesn't touch any firmware files. It may not fully fix the hang, but it's worth trying, and the log it produces helps us if it doesn't: 

#!/usr/bin/env bash
# wifi_calibration_probe.sh -- run with: sudo bash wifi_calibration_probe.sh
set -euo pipefail
[ "$(id -u)" -eq 0 ] || { echo "Run with sudo."; exit 1; }
LOG="$HOME/selahos-wifi-probe-$(date +%Y%m%d-%H%M%S).log"
{
  echo "=== before ==="; iw reg get || true
  echo "=== setting regulatory domain (edit 'US' if you're elsewhere) ==="
  iw reg set US; sleep 1; iw reg get
  nmcli radio wifi off || true
  modprobe -r brcmfmac || true
  sleep 2
  modprobe brcmfmac
  sleep 3
  nmcli radio wifi on
  echo "=== now try connecting -- watching logs for 60s ==="
  timeout 60 journalctl -k -f &
  timeout 60 journalctl -u NetworkManager -f &
  wait
  nmcli device status
} 2>&1 | tee "$LOG"
echo "Send us $LOG regardless of the outcome: beta@selahos.io"

If you find a fix — a real per-board NVRAM/CLM file for your exact model, or anything else that reliably works — please email beta@selahos.io. We'd rather ship your verified fix than wait on our own testing queue.

Internal speaker silent on some Cirrus CS4208 Macs Active

On Macs using the Cirrus Logic CS4208 audio codec (confirmed so far: MacBook 10,1 and iMac16,2 — the 12" MacBook and the 2015 21.5" iMac), the internal speaker produces no sound, even though the driver loads correctly and every software-level signal (volume, routing, the codec itself) checks out fine. This points to something at the hardware amplifier-enable level that hasn't been correctly reproduced yet, not a configuration mistake.

Workaround

Use the headphone jack or an external/USB audio device. The headphone output on this same codec has been confirmed working — it's only the internal speaker path that's affected.

Technical detail + an experiment to try (advanced users, local access only)

Every register the current driver touches is already in the state it intends to be in — the speaker pin is correctly wired, volume is at 100%, and the presumed amplifier-enable GPIO line is being driven high — and it's still silent. This script lets you try other GPIO bit patterns live, in seconds, instead of a full rebuild per guess. It must be run from a terminal in your own local desktop session on the machine — not over SSH (a kernel security policy blocks this kind of raw hardware access from remote sessions). 

#!/usr/bin/env python3
# gpio_poke.py -- usage: python3 gpio_poke.py 0x31
# Try, one at a time, while a continuous tone plays in another terminal
# (speaker-test -D default -c2 -t sine -f 440 -l 0), listening after each:
#   0x31  0x11  0x21  0x30  0x10  0x20  0x00
import fcntl, glob, struct, sys
HDA_IOCTL_VERB_WRITE = 0xC0084811
AFG_NID, AC_VERB_SET_GPIO_DATA = 0x01, 0x715
def hda_verb(nid, verb, param): return (nid << 24) | (verb << 8) | param
data = int(sys.argv[1], 16) & 0xFF
dev = sorted(glob.glob("/dev/snd/hwC*D0"))[0]
buf = bytearray(struct.pack("=II", hda_verb(AFG_NID, AC_VERB_SET_GPIO_DATA, data), 0))
with open(dev, "rb+", buffering=0) as f:
    fcntl.ioctl(f.fileno(), HDA_IOCTL_VERB_WRITE, buf, True)
print(f"Wrote GPIO_DATA=0x{data:02x} via {dev}. Listen now.")

If any value produces real audible sound, stop and email us the exact value at beta@selahos.io — that's the missing piece we need to make it permanent.
